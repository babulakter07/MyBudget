Project: `D:\MyProject\MyBudget`. **Read `CLAUDE.md`, `docs/AGENT_BRIEF.md` and `docs/AGENT_BRIEF_V4.md` first; all their rules still apply** (material_ui imports only, locked heavy commands, never run build_runner / `pub get`, never kill processes, own only your folders). This sprint changes **strings only**: no behaviour, schema, layout or logic changes.

## How localization works here (already set up by the lead)
- `lib/l10n/l10n.dart` exports the generated `AppLocalizations` and the extension **`context.l10n.<key>`** (falls back to English when a test builds a bare `MaterialApp`, so existing tests keep working).
- You write ARB **parts**, never `lib/l10n/*.arb`: `l10n_parts/<module>_en.arb` and `l10n_parts/<module>_bn.arb`, where `<module>` is the snake_case module name you were given (e.g. `cost_items`). **Every key must start with the camelCase module name** (`cost_items` -> `costItems...`, `transactions` -> `transactions...`). Reusable generic words already exist in `l10n_parts/common_*.arb` (keys `commonOk`, `commonCancel`, `commonSave`, `commonDelete`, `commonEdit`, `commonAdd`, `commonClose`, `commonRetry`, `commonUndo`, `commonSearch`, `commonLoading`, `commonYes`, `commonNo`, `commonDone`, `commonNext`, `commonBack`, `commonConfirm`, `commonShare`, `commonCreate`, `commonUpdate`, `commonRemove`, `commonActive`, `commonInactive`, `commonArchive`, `commonRestore`, `commonClear`, `commonApply`, `commonAll`, `commonNone`, `commonOptional`, `commonRequired`, `commonSelectProfile`, `commonNoData`, `commonSomethingWentWrong`) — use those instead of duplicating; do NOT edit the common parts (ask in your report for additions).
- After editing parts run **`tool/l10n.sh`** (merges parts with duplicate/parity/placeholder checks, then runs `flutter gen-l10n`; serialised by the lock; takes seconds). Fix whatever it reports. Then your code can use the new getters/methods.
- `python tool/find_hardcoded.py lib/features/<yours>` lists remaining user-facing literals in your folders (heuristic; also read your files). Goal: zero real user-facing English literals left in your presentation code and message builders.

## Rules
1. **English text must stay exactly as it is today** (existing tests find widgets by English text). Move the current string into `*_en.arb` verbatim. Remove `const` from widgets that now call `context.l10n`.
2. Strings with values use ICU placeholders: `"transactionsDeleted": "Deleted {title}"` and a metadata entry in the **English** part: `"@transactionsDeleted": {"placeholders": {"title": {"type": "String"}}}`. Types: `String`, `int`, `num`, `DateTime` (then add `"format": "yMMMd"`), pass already-formatted money as `String` (keep using `formatMinor`). Plurals: `"{count, plural, =0{No items} =1{1 item} other{{count} items}}"` with `count` as `int`. Every key that has placeholders needs `@key` metadata (a parity test enforces it).
3. Bangla (`*_bn.arb`): natural, concise Bangla for a personal-finance app (taka, খরচ = expense, আয় = income, হিসাব = account, বাজেট, লেনদেন = transaction, ক্যাটাগরি, সঞ্চয় = savings, ঋণ = debt/loan, ব্যালেন্স). Same placeholders as English. Do not leave English text in Bangla values (a test checks), except unavoidable tokens like currency codes, which should be placeholders instead of literals.
4. **Never translate user data** (profile/account/category names etc.). Enum-like values stored in the DB (`expense`, `income`, `transfer`, account types, frequencies, directions `lent`/`borrowed`, `monthly`) keep their stored form; only their DISPLAY labels are localized.
5. Pure functions that build user-facing sentences (e.g. insight messages, reminder text, report headings) take an `AppLocalizations` parameter instead of hard-coding English; update their callers and tests accordingly. Code with no `BuildContext` (background notifications) gets the language via `lookupAppLocalizations(locale)` from `lib/l10n/generated/app_localizations.dart`, where `locale` is the saved app language (`localeProvider` in `lib/features/preferences/data/locale_provider.dart`) or the platform locale if none, falling back to `Locale('en')`.
6. **Out of scope (leave English, list them in your report):** exception messages thrown by repositories/services (`AppException` subclasses) and `ValidationException` text, PDF/CSV export content and file names, log text, notification channel ids. Messages that a screen builds itself from its own checks (e.g. form validators in the widget) ARE in scope.
7. Dates/numbers: use the existing `intl` formatters without a hard-coded locale (the app sets `Intl.defaultLocale`); money stays `formatMinor` (ASCII digits, ৳).
8. Tests: existing tests must keep passing unchanged except where a pure function gained an `AppLocalizations` parameter. Add Bangla tests in `test/<module>_l10n_test.dart` using `test/l10n_test_helpers.dart` (`localizedApp(home: ...)`, wrap in your own `ProviderScope`): pump your main screen(s) in `bn`, assert a few representative Bangla strings render and `tester.takeException()` is null. Also assert one English smoke (default test app) still shows the English text.
9. Format only your own paths (`dart format lib/features/<yours> test/<yours>`). Analyze only your paths via `tool/locked.sh dart analyze ...`. Run your tests via `tool/locked.sh flutter test test/<yours> ...`.
